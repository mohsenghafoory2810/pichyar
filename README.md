## امکانات سایت

- اسکلت سایت فارسی و راست‌چین، مناسب موبایل، با فونت وزیرمتن.
- پنجرهٔ تأیید سن (بالای ۱۸ سال) در اولین بازدید؛ تأیید تا ۳۰ روز در مرورگر بازدیدکننده می‌ماند.
- صفحهٔ اصلی با بنرها و دو بخش «توتون» و «لوازم».
- فهرست محصولات هر دسته با جستجو، مرتب‌سازی (ارزان‌ترین، گران‌ترین، جدیدترین) و صفحه‌بندی؛ صفحهٔ هر محصول با گالری تصویر، قیمت، واحد و وضعیت موجودی.
- مدیریت محصولات: ویرایش قیمت و موجودی مستقیم در فهرست، چند تصویر برای هر محصول، تاریخچهٔ تغییر قیمت، به‌روزرسانی گروهی با اکسل یا با درصد/مبلغ ثابت.
- صفحه‌های ثابت قابل ویرایش: درباره ما، تماس با ما، شیوهٔ ارسال، قوانین و مقررات، حریم خصوصی.
- تنظیمات سایت در پنل مدیریت: نام سایت، لوگو، تلفن، اطلاعات پشتیبانی، شماره کارت‌ها و «حالت تعمیر».
- پشتیبان‌گیری خودکار روزانه از پایگاه داده (ساعت ۳:۳۰ بامداد، ۱۴ نسخهٔ آخر نگه داشته می‌شود).
- HTTPS خودکار (گواهی رایگان).

- ورود و ثبت‌نام با شمارهٔ موبایل و کد پیامکی؛ پنل کاربری (سفارش‌ها، نشانی‌ها، مشخصات).
- سبد خرید (برای مهمان هم)، تسویه حساب یک‌صفحه‌ای، هزینهٔ ارسال پستی پله‌ای، پرداخت اینترنتی (زرین‌پال) و کارت به کارت، پیگیری سفارش.
- کد تخفیف (درصدی یا مبلغ ثابت، با سقف، حداقل خرید، تاریخ و محدودیت استفاده) و هدیهٔ انتخابی به ازای هر پلهٔ خرید.
- پیامک با کاوه‌نگار (قابل تغییر به سرویس دیگر)، متن‌های قابل ویرایش، گزارش پیامک‌ها با تلاش دوباره، و پیامک سفارش جدید به مدیر.
- پیشخوان مدیریت: فروش امروز / این هفته / این ماه، سفارش‌های منتظر تأیید و ارسال، محصولات کم‌موجود و نمودار فروش ۳۰ روز اخیر.
- مدیریت سفارش‌ها: جستجو و فیلتر، تأیید یا رد کارت به کارت با دیدن عکس رسید، ثبت ارسال با کد رهگیری پست (همراه پیامک به مشتری)، تحویل، لغو (با برگشت موجودی)، چاپ برگهٔ بسته‌بندی و برچسب نشانی، خروجی اکسل.
- فهرست مشتریان با تاریخچهٔ سفارش‌ها.
- امنیت: قفل شدن ورود پنل پس از چند تلاش ناموفق، ورود دومرحله‌ای اختیاری (Google Authenticator)، HTTPS اجباری.

> **تا وقتی کلید سرویس پیامک را وارد نکرده‌اید، پیامکی فرستاده نمی‌شود** و متن پیامک‌ها (از جمله کد ورود) فقط در گزارش برنامه نوشته می‌شود: `docker compose logs --tail=50 app`. پیش از باز کردن سایت برای فروش، بخش [پیامک](#پیامک) را انجام دهید.

## ۱. خرید سرور مجازی (VPS)

از یک شرکت ارائه‌دهندهٔ سرور، یک **سرور مجازی (VPS)** با این مشخصات بخرید:

| مورد | مقدار |
|---|---|
| سیستم‌عامل | **Ubuntu 24.04** |
| پردازنده | ۲ هسته (2 vCPU) |
| حافظه | ۲ گیگابایت (2 GB RAM) |
| فضای دیسک | دست‌کم ۴۰ گیگابایت SSD |

بعد از خرید، این سه چیز را از شرکت می‌گیرید (معمولاً ایمیل می‌شود): **آی‌پی سرور** (مثل `185.10.20.30`)، **نام کاربری** (معمولاً `root`) و **رمز عبور**. آن‌ها را جایی امن یادداشت کنید.

## ۲. وصل کردن دامنه به سرور

در پنل شرکتی که دامنه را از آن خریده‌اید (یا پنل DNS، مثلاً ابر آروان یا Cloudflare)، یک رکورد بسازید:

| نوع (Type) | نام (Name) | مقدار (Value) |
|---|---|---|
| `A` | `@` | آی‌پی سرور شما |

اگر از Cloudflare یا ابر آروان استفاده می‌کنید، در ابتدا **پروکسی (ابر نارنجی/حالت CDN) را خاموش** کنید تا گواهی HTTPS بدون مشکل صادر شود.

اعمال این تغییر ممکن است از چند دقیقه تا چند ساعت طول بکشد. برای اطمینان، در سایت <https://dnschecker.org> نام دامنه را بزنید و ببینید آی‌پی سرورتان نشان داده می‌شود.

## ۳. وصل شدن به سرور

- **ویندوز ۱۰ و ۱۱:** برنامهٔ «PowerShell» را باز کنید.
- **مک:** برنامهٔ «Terminal» را باز کنید.

سپس بنویسید (به‌جای آی‌پی، آی‌پی سرور خودتان):

```bash
ssh root@<آی‌پی-سرور>
```

اولین بار می‌پرسد مطمئن هستید یا نه؛ بنویسید `yes` و Enter بزنید. بعد رمز سرور را وارد کنید (هنگام تایپ رمز چیزی نمایش داده نمی‌شود؛ طبیعی است).

از این‌جا به بعد همهٔ دستورها **روی سرور** اجرا می‌شوند.

## ۴. نصب Docker

این دستورها را یکی‌یکی اجرا کنید:

```bash
apt update && apt upgrade -y
apt install -y docker.io docker-compose-v2 git
systemctl enable --now docker
```

برای امنیت، فقط درگاه‌های لازم را باز کنید:

```bash
ufw allow 22
ufw allow 80
ufw allow 443
ufw --force enable
```

برای اطمینان از نصب درست:

```bash
docker compose version
```

باید شماره‌ای مثل `Docker Compose version v2...` ببینید.

## ۵. گذاشتن برنامه روی سرور و تنظیمات

**روش اول (پیشنهادی): از مخزن گیت**

```bash
cd /opt
git clone <نشانی-مخزن-گیت> pichyar
cd /opt/pichyar
```

**روش دوم: فایل فشرده.** پوشهٔ پروژه را روی رایانهٔ خودتان zip کنید و از PowerShell/Terminal **رایانهٔ خودتان** (نه سرور) بفرستید:

```bash
scp pichyar.zip root@<آی‌پی-سرور>:/opt/
```

سپس روی سرور:

```bash
apt install -y unzip
cd /opt && unzip pichyar.zip && cd /opt/pichyar
```

**ساخت فایل تنظیمات:**

```bash
cp .env.example .env
openssl rand -hex 32
```

دستور دوم یک رشتهٔ طولانی تصادفی چاپ می‌کند؛ آن را کپی کنید. حالا فایل تنظیمات را باز کنید:

```bash
nano .env
```

این موارد را پر کنید:

| تنظیم | توضیح |
|---|---|
| `DOMAIN` | دامنهٔ شما بدون `https://`، مثلاً `pichyar.ir` |
| `ACME_EMAIL` | ایمیل شما (برای گواهی HTTPS) |
| `SECRET_KEY` | همان رشتهٔ تصادفی که کپی کردید |
| `ADMIN_URL` | نشانی پنل مدیریت؛ یک کلمهٔ غیرقابل‌حدس، مثلاً `panel-k39x/`. اگر `admin/` یا همان `panel-change-me/` بماند، **سایت روشن نمی‌شود** |
| `DJANGO_SUPERUSER_MOBILE` | شمارهٔ موبایل مدیر، مثلاً `09121234567` (نام کاربری پنل مدیریت همین شماره است) |
| `DJANGO_SUPERUSER_PASSWORD` | یک رمز قوی (دست‌کم ۱۲ حرف، ترکیب حرف و عدد) |

برای ذخیره: `Ctrl+O` و بعد `Enter`. برای خروج: `Ctrl+X`.

بقیهٔ خانه‌های `.env` را می‌توانید همان‌طور که هست بگذارید (توضیح همه در [جدول متغیرها](#متغیرهای-env) آمده است). تنظیمات پیامک، درگاه، کارت‌ها، هزینهٔ ارسال و هدیه در `.env` **نیستند**؛ آن‌ها را بعداً در پنل مدیریت وارد می‌کنید.

> فایل `.env` رمزهای سایت را دارد: آن را برای کسی نفرستید و در گیت قرار ندهید (پروژه طوری تنظیم شده که گیت آن را نادیده بگیرد).

## ۶. راه‌اندازی سایت

```bash
cd /opt/pichyar
docker compose up -d --build
```

بار اول ممکن است ۵ تا ۱۵ دقیقه طول بکشد. بعد از آن وضعیت را ببینید:

```bash
docker compose ps
```

هر سه سرویس (`app`، `worker`، `caddy`) باید `running` یا `healthy` باشند (سرویس `worker` حداکثر دو دقیقه بعد از بقیه سالم می‌شود). حالا آدرس `https://<دامنهٔ-شما>` را در مرورگر باز کنید.

همهٔ کارهای لازم (ساخت پایگاه داده، آماده‌سازی فایل‌ها و ساخت کاربر مدیر) **خودکار** انجام می‌شود.

## ۷. پنل مدیریت: اولین ورود و تنظیمات

### ساخت کاربر مدیر

کاربر مدیر **خودکار** ساخته می‌شود: بار اول که سایت روشن می‌شود، اگر هنوز مدیری نباشد، با `DJANGO_SUPERUSER_MOBILE` و `DJANGO_SUPERUSER_PASSWORD` فایل `.env` ساخته می‌شود. برای اطمینان:

```bash
docker compose logs app | grep -i superuser
```

باید `Superuser '09...' created.` ببینید. اگر رمز را در `.env` خالی گذاشته بودید، مدیر را دستی بسازید:

```bash
docker compose exec app python manage.py createsuperuser
```

(شمارهٔ موبایل و دو بار رمز را می‌پرسد.) برای افزودن مدیر دوم: در پنل، **کاربران و امنیت ← کاربران و مدیران ← افزودن**؛ سپس تیک «وضعیت کارمندی» (برای دسترسی به پنل) و در صورت نیاز «ابرکاربر» (دسترسی کامل) را بزنید.

### اولین ورود

آدرس پنل: `https://<دامنهٔ-شما>/<ADMIN_URL>` — مثلاً `https://pichyar.ir/panel-k39x/`

با **شمارهٔ موبایل** (به‌عنوان نام کاربری) و **رمز** وارد شوید. خانهٔ «کد ورود دومرحله‌ای» را فعلاً خالی بگذارید. (اگر سایت را پیش از این مرحله راه‌انداخته‌اید، مدیر قبلی همچنان با همان نام کاربری قبلی، مثلاً `admin`، وارد می‌شود؛ در «کاربران» شمارهٔ موبایلش را وارد کنید.)

> ورود با کد پیامکی از صفحهٔ «ورود» فروشگاه، فقط حساب مشتری را باز می‌کند؛ پنل مدیریت **همیشه** رمز می‌خواهد.

صفحهٔ اول پنل، **پیشخوان** است: فروش امروز / این هفته / این ماه (فقط سفارش‌های پرداخت‌شده، بر اساس تقویم شمسی و هفته از شنبه)، تعداد سفارش‌های «در انتظار تأیید کارت به کارت» و «آمادهٔ ارسال»، محصولات کم‌موجود و نمودار فروش روزانهٔ ۳۰ روز اخیر (ماوس را روی هر ستون نگه دارید؛ جدول همان عددها زیر نمودار است). منوی کنار صفحه این بخش‌ها را دارد: **فروش** (سفارش‌ها، مشتریان، کدهای تخفیف، کالاهای هدیه)، **محصولات**، **محتوای سایت** (بنرها، صفحه‌های ثابت)، **پیامک**، **تنظیمات**، **کاربران و امنیت** و **سیستم**.

### پر کردن تنظیمات سایت (به ترتیب)

همه در **تنظیمات ← تنظیمات سایت**، که در ۸ بخش شماره‌دار مرتب شده است:

| بخش | چه چیزی | راهنمای کامل |
|---|---|---|
| ۱. مشخصات فروشگاه | نام سایت، لوگو (JPG/PNG/WebP)، تلفن و اطلاعات پشتیبانی | — |
| ۲. تعمیر و نگهداری | بستن موقت سایت با یک پیام | پایین همین بخش |
| ۳. هزینهٔ ارسال | مبلغ هر پله، هزینهٔ هر پله، گرد کردن | [هزینهٔ ارسال](#هزینهٔ-ارسال-فقط-پست) |
| ۴. هدیه | روشن/خاموش و مبلغ خرید برای هر هدیه | [هدیه](#هدیه) |
| ۵. پرداخت اینترنتی | درگاه، مرچنت کد، حالت آزمایشی | [درگاه پرداخت](#راهاندازی-درگاه-پرداخت-زرینپال) |
| ۶. کارت به کارت | روشن/خاموش؛ شماره کارت‌ها و نام صاحب کارت در جدول پایین صفحه | [کارت به کارت](#کارت-به-کارت) |
| ۷. سرویس پیامک | سرویس، کلید API، شمارهٔ فرستنده | [پیامک](#پیامک) |
| ۸. پیامک مدیر | شماره‌های موبایل مدیر و روشن/خاموش | [پیامک مدیر](#پیامک-سفارش-جدید-به-مدیر) |

**رمزها نمایش داده نمی‌شوند:** «کلید API پیامک» و «شناسهٔ پذیرنده» بعد از ذخیره فقط به شکل `••••••••abcd` (چهار نویسهٔ آخر) دیده می‌شوند. اگر خانه را خالی بگذارید و ذخیره کنید، مقدار قبلی **می‌ماند**. برای عوض کردن، مقدار جدید را بنویسید؛ برای پاک کردن، تیک «پاک کردن …» زیر آن را بزنید.

بعد از تنظیمات:

1. **صفحه‌های ثابت** (محتوای سایت ← صفحه‌های ثابت): متن «درباره ما»، «قوانین و مقررات» و بقیه را بنویسید.
2. **بنرهای صفحهٔ اصلی** (محتوای سایت ← بنرها): تصویرها را بارگذاری کنید (JPG، PNG یا WebP؛ اندازهٔ پیشنهادی ۱۶۰۰×۶۴۰ پیکسل). با «ترتیب» جای هر بنر مشخص می‌شود.
3. **محصولات:** [بخش ۱۱](#۱۱-محصولات-موجودی-و-قیمتها) (افزودن محصول و تصویر، موجودی، تغییر گروهی قیمت با اکسل).
4. **ورود دومرحله‌ای** را برای خودتان روشن کنید: [بخش ۱۵](#۱۵-امنیت-پنل-مدیریت).

**حالت تعمیر:** در «تنظیمات سایت» گزینهٔ «حالت تعمیر و نگهداری» را روشن کنید تا بازدیدکنندگان پیام «در حال به‌روزرسانی» ببینند. شما که وارد پنل شده‌اید سایت را عادی می‌بینید.

**اگر رمز مدیر را فراموش کردید:**

```bash
cd /opt/pichyar
docker compose exec app python manage.py changepassword <شمارهٔ-موبایل-مدیر>
```

## ۸. به‌روزرسانی سایت

وقتی نسخهٔ جدیدی از برنامه آماده شد:

```bash
cd /opt/pichyar
docker compose exec worker python manage.py backup_db
git pull
docker compose up -d --build
```

دستور اول قبل از به‌روزرسانی یک نسخهٔ پشتیبان تازه می‌گیرد. اگر برنامه را با فایل zip فرستاده‌اید، به‌جای `git pull` فایل‌های جدید را جایگزین کنید (فایل `.env` را پاک نکنید).

تغییرات پایگاه داده (migration) هنگام روشن شدن خودکار اعمال می‌شود. پس از چند دقیقه `docker compose ps` را بزنید؛ هر سه سرویس باید `healthy` باشند. اگر نسخهٔ جدید خانهٔ تازه‌ای در `.env.example` دارد، آن را با `nano .env` به `.env` خودتان اضافه کنید (`diff .env.example .env` تفاوت‌ها را نشان می‌دهد).

برای پاک کردن تصویرهای قدیمی Docker و آزاد کردن دیسک (گاهی، مثلاً ماهی یک بار): `docker image prune -f`

## ۹. پشتیبان‌گیری و بازگردانی

**پشتیبان خودکار:** هر شب ساعت ۳:۳۰ (به وقت تهران) یک نسخه از پایگاه داده ذخیره می‌شود و ۱۴ نسخهٔ آخر نگه داشته می‌شود (تعداد با `BACKUP_KEEP` در `.env` قابل تغییر است).

**گرفتن پشتیبان همین الان:**

```bash
cd /opt/pichyar
docker compose exec worker python manage.py backup_db
```

**دیدن فهرست پشتیبان‌ها:**

```bash
sh scripts/restore.sh
```

**بردن پشتیبان‌ها به رایانهٔ خودتان (توصیهٔ جدی: هفته‌ای یک بار).** روی سرور:

```bash
cd /opt/pichyar
docker compose cp worker:/app/data/backups ./backups-copy
```

سپس روی **رایانهٔ خودتان**:

```bash
scp -r root@<آی‌پی-سرور>:/opt/pichyar/backups-copy ./
```

> این پشتیبان فقط شامل **پایگاه داده** است (محصولات، سفارش‌ها، تنظیمات، صفحه‌ها و…). عکس‌های بارگذاری‌شده (محصولات، بنرها، لوگو) و عکس رسیدهای کارت به کارت را هم این‌طور کپی کنید:
> ```bash
> docker compose cp app:/app/data/media ./media-copy
> docker compose cp app:/app/data/private ./private-copy
> ```
> و برای برگرداندنشان (مثلاً روی سرور جدید):
> ```bash
> docker compose cp ./media-copy/. app:/app/data/media
> docker compose cp ./private-copy/. app:/app/data/private
> ```

**انتقال به سرور جدید:** روی سرور جدید بخش‌های ۴ تا ۶ را انجام دهید (همان `.env` قبلی را کپی کنید؛ مخصوصاً `SECRET_KEY` باید همان باشد)، سپس پشتیبان پایگاه داده را مثل پایین بازگردانی کنید و پوشه‌های media و private را مثل بالا برگردانید. در آخر رکورد DNS دامنه را به آی‌پی جدید عوض کنید.

**بازگردانی یک پشتیبان:**

```bash
cd /opt/pichyar
sh scripts/restore.sh db-20250101-033000.sqlite3
```

(نام فایل را از فهرست پشتیبان‌ها بردارید.) این دستور سایت را چند ثانیه متوقف می‌کند، پایگاه داده را با نسخهٔ پشتیبان جایگزین می‌کند و دوباره سایت را روشن می‌کند. **هر تغییری که بعد از زمان آن پشتیبان انجام شده از بین می‌رود.**

**بازگردانی پشتیبانی که روی رایانهٔ شماست:** اول فایل را به سرور بفرستید (از رایانهٔ خودتان):

```bash
scp db-20250101-033000.sqlite3 root@<آی‌پی-سرور>:/opt/pichyar/
```

سپس روی سرور:

```bash
cd /opt/pichyar
docker compose cp db-20250101-033000.sqlite3 worker:/app/data/backups/
sh scripts/restore.sh db-20250101-033000.sqlite3
```

## ۱۰. عیب‌یابی

| مشکل | کار لازم |
|---|---|
| دیدن گزارش‌ها (لاگ) | `docker compose logs --tail=100 app` (به‌جای `app` می‌توانید `worker` یا `caddy` بنویسید) |
| فایل خطاهای برنامه | `docker compose exec app tail -n 50 /app/data/logs/errors.log` |
| بررسی سلامت سایت | آدرس `https://<دامنه>/health` باید `{"status": "ok"}` نشان دهد |
| سایت با HTTPS باز نمی‌شود | مطمئن شوید رکورد DNS درست است و پروکسی Cloudflare/آروان خاموش است؛ سپس `docker compose restart caddy` |
| روشن/خاموش کردن دوبارهٔ همه | `docker compose restart` |
| سرویس `app` مدام دوباره روشن می‌شود (`Restarting`) | `docker compose logs --tail=50 app`. اگر `ImproperlyConfigured` دیدید: `SECRET_KEY` خالی یا کوتاه است، یا `ADMIN_URL` هنوز `admin/` یا `panel-change-me/` است. `.env` را درست کنید و `docker compose up -d` |
| «ورود به پنل مدیریت موقتاً بسته شد» | پس از ۵ رمز یا کد اشتباه، ورود از آن اینترنت ۱ ساعت بسته می‌شود. صبر کنید یا: `docker compose exec app python manage.py axes_reset` |
| رمز مدیر را فراموش کرده‌اید | `docker compose exec app python manage.py changepassword <موبایل-مدیر>` |
| گوشی ورود دومرحله‌ای گم شده | `docker compose exec app python manage.py disable_2fa <موبایل-مدیر>`؛ بعد با رمز وارد شوید و دوباره روشنش کنید |
| کد ورود پیامکی به مشتری‌ها نمی‌رسد | **پیامک ← گزارش پیامک‌ها**؛ ستون «خطا» را ببینید (بخش [پیامک](#پیامک)). کلید API در تنظیمات خالی نباشد و کانتینر `worker` سالم باشد |
| پرداخت اینترنتی در صفحهٔ خرید نیست | «پرداخت اینترنتی فعال باشد» روشن و «شناسهٔ پذیرنده» پر باشد |
| `worker` سالم (`healthy`) نیست | `docker compose logs --tail=50 worker` و `docker compose restart worker` |
| دیسک پر شده | `df -h`؛ سپس `docker image prune -f` و `docker builder prune -f` |
| فایل اکسل خروجی در اکسل به‌هم‌ریخته است | فایل را با «Microsoft Excel» یا «LibreOffice» باز کنید (نه با برنامهٔ دیگری)؛ فایل راست‌به‌چپ و UTF-8 است |

**اگر سرور داخل ایران است:** ممکن است دریافت فایل‌ها از Docker Hub، GitHub یا PyPI مسدود باشد و مرحلهٔ `--build` خطا بدهد. در این حالت از پشتیبانی شرکت سرور بپرسید «آینهٔ داکر (Docker registry mirror)» چه آدرسی دارد، یا از آینه‌های عمومی (مثل آینهٔ ابر آروان) استفاده کنید. یک راه ساده‌تر: ساخت را روی سروری خارج از ایران انجام دهید.


## ۱۱. محصولات، موجودی و قیمت‌ها

همهٔ این کارها در پنل مدیریت، بخش **«کاتالوگ محصولات»** انجام می‌شود.

### بارگذاری فهرست اولیهٔ محصولات (فقط یک بار)

```bash
cd /opt/pichyar
docker compose exec app python manage.py seed_products
```

این دستور ۶۲ محصول (۳۲ توتون و ۳۰ قلم لوازم) را با قیمت‌های اولیه، **موجودی صفر** و یک تصویر ساده می‌سازد. اجرای دوباره‌اش ضرری ندارد: محصولی که از قبل هست دست نمی‌خورد، پس قیمت و موجودی‌ای که خودتان وارد کرده‌اید پاک نمی‌شود.

> چون موجودی همه صفر است، در سایت همه «ناموجود» نشان داده می‌شوند. بعد از اجرای دستور، موجودی‌ها را وارد کنید (پایین‌تر توضیح داده شده).

### دسته‌بندی‌ها

دو دستهٔ اصلی «توتون» و «لوازم» از قبل ساخته شده‌اند. «لوازم» این زیردسته‌ها را دارد: دستگاه‌ها، پوکه، پیپر، فیلتر، چوب سیگار، پیپ، سیگار برگ، سایر.

- دسته‌بندی حداکثر **دو سطح** دارد (دستهٔ اصلی ← زیردسته).
- با «ترتیب» جای دسته‌ها مشخص می‌شود. اگر «فعال» را بردارید، آن دسته و محصولاتش در سایت دیده نمی‌شوند.
- در صفحهٔ اصلی سایت برای هر دستهٔ اصلی یک بخش نمایش داده می‌شود.

### افزودن یا ویرایش یک محصول

**کاتالوگ محصولات ← محصولات ← افزودن محصول.** مهم‌ترین خانه‌ها:

| خانه | توضیح |
|---|---|
| نام | نامی که مشتری می‌بیند |
| نام کوتاه | برای پیامک‌های مدیر؛ اگر خالی بماند همان نام گذاشته می‌شود |
| نشانی (slug) | خالی بگذارید تا خودکار از روی نام ساخته شود |
| قیمت (تومان) | فقط عدد، بدون جداکننده؛ مثلاً `750000` |
| واحد فروش | مثلاً «۵۰ گرم» یا «عدد» |
| موجودی | تعداد موجود در انبار. صفر یعنی «ناموجود» و مشتری نمی‌تواند آن را بخرد |
| آستانهٔ کمبود موجودی | وقتی موجودی به این عدد یا کمتر برسد، ردیف محصول در فهرست مدیریت رنگی می‌شود |
| ترتیب نمایش | عدد کمتر یعنی بالاتر در فهرست |

**تصویرها:** پایین همان صفحه، با «افزودن تصویر محصول دیگر» هر چند تصویر که بخواهید اضافه کنید (JPG، PNG یا WebP، هر کدام حداکثر ۵ مگابایت). تصویرها خودکار کوچک و به WebP تبدیل می‌شوند تا سایت سریع بماند. ردیف‌ها را **با کشیدن و رها کردن** جابه‌جا کنید؛ **اولین تصویر، تصویر اصلی** است. اندازهٔ پیشنهادی: مربع، دست‌کم ۱۰۰۰×۱۰۰۰ پیکسل.

**تاریخچهٔ قیمت:** پایین صفحهٔ هر محصول، بخش «تاریخچهٔ تغییر قیمت» (روی آن بزنید تا باز شود) نشان می‌دهد قیمت چه زمانی، از چه مبلغی به چه مبلغی و توسط چه کسی عوض شده است. هر تغییر قیمت، از هر راهی (ویرایش، فهرست، اکسل یا تغییر گروهی)، خودکار ثبت می‌شود.

### تغییر سریع قیمت و موجودی در فهرست

در فهرست محصولات، خانه‌های **قیمت** و **موجودی** همان‌جا قابل ویرایش‌اند. عددها را عوض کنید و پایین صفحه **«ذخیره»** را بزنید.

- ستون «وضعیت موجودی»: ردیف‌های **زرد** به آستانهٔ کمبود رسیده‌اند و ردیف‌های **قرمز** ناموجودند.
- از ستون کناری می‌توانید بر اساس دسته‌بندی (انتخاب دستهٔ اصلی، زیردسته‌هایش را هم نشان می‌دهد)، فعال بودن و وضعیت موجودی فیلتر کنید. کادر جستجوی بالای فهرست در نام محصولات جستجو می‌کند.

### به‌روزرسانی گروهی با اکسل

مناسب وقتی که قیمت یا موجودی تعداد زیادی محصول را با هم عوض می‌کنید.

1. در فهرست محصولات، بالای صفحه **«خروجی»** را بزنید و فایل اکسل (`xlsx`) را بگیرید.
2. فایل را در اکسل باز کنید و فقط ستون‌های **«قیمت (تومان)»** و **«موجودی»** را عوض کنید. ستون «شناسه» را تغییر ندهید و ردیف جدید اضافه نکنید (از اکسل محصول جدید ساخته نمی‌شود). ستون‌های نام، دسته و واحد فقط برای راهنمایی‌اند و تغییرشان اثری ندارد.
3. فایل را ذخیره کنید (همان قالب xlsx).
4. در فهرست محصولات **«بارگذاری»** را بزنید، فایل را انتخاب کنید و «ارسال» را بزنید.
5. یک **پیش‌نمایش** می‌بینید: کدام محصولات عوض می‌شوند و کدام بی‌تغییرند. اگر خطایی باشد (مثلاً متن به‌جای عدد، عدد منفی یا اعشاری، خانهٔ خالی یا شناسه‌ای که وجود ندارد)، ردیف و دلیل خطا نشان داده می‌شود و **هیچ تغییری ذخیره نمی‌شود**؛ فایل را درست کنید و دوباره وارد کنید.
6. اگر همه چیز درست بود، **«تایید بارگذاری»** را بزنید. فقط در این مرحله تغییرها ذخیره می‌شوند.

عددها را می‌توانید با رقم فارسی یا انگلیسی و با یا بدون جداکنندهٔ هزارگان بنویسید (`750000`، `750,000` یا `۷۵۰٬۰۰۰`).

### افزایش یا کاهش گروهی قیمت (درصدی یا مبلغ ثابت)

**برای چند محصول دلخواه:** در فهرست محصولات، کنار محصولات مورد نظر تیک بزنید، از منوی «عملیات» گزینهٔ **«تغییر گروهی قیمت محصولات انتخاب‌شده»** را انتخاب کنید و «اجرا» را بزنید.

**برای یک دستهٔ کامل:** بالای فهرست محصولات **«تغییر قیمت یک دسته»** را بزنید و دسته را انتخاب کنید. اگر دستهٔ اصلی (مثلاً «لوازم») را انتخاب کنید، همهٔ زیردسته‌هایش هم تغییر می‌کنند.

سپس:

1. **جهت تغییر:** افزایش یا کاهش.
2. **نوع تغییر:** درصدی (مثلاً `10` یعنی ۱۰٪) یا مبلغ ثابت به تومان (مثلاً `50000`).
3. **گرد کردن قیمت جدید:** بدون گرد کردن، یا به نزدیک‌ترین ۱٬۰۰۰ / ۵٬۰۰۰ / ۱۰٬۰۰۰ تومان. مثال: ۳۷۵٬۰۰۰ با ۱۰٪ افزایش می‌شود ۴۱۲٬۵۰۰؛ با گرد کردن به ۱٬۰۰۰ می‌شود ۴۱۳٬۰۰۰، به ۵٬۰۰۰ می‌شود ۴۱۵٬۰۰۰ و به ۱۰٬۰۰۰ می‌شود ۴۱۰٬۰۰۰ (نیمه به بالا گرد می‌شود).
4. **«پیش‌نمایش»** را بزنید تا قیمت فعلی و جدید هر محصول را ببینید. هنوز چیزی ذخیره نشده است.
5. اگر درست بود، **«اعمال تغییرات»** را بزنید.

اگر تغییری باعث شود قیمت محصولی صفر یا منفی شود، هیچ قیمتی تغییر نمی‌کند و نام آن محصولات نشان داده می‌شود.

### نمایش در سایت

- محصول با موجودی صفر برچسب **«ناموجود»** می‌گیرد، تصویرش کم‌رنگ می‌شود و قابل خرید نیست.
- برای پنهان کردن یک محصول بدون پاک کردنش، «فعال» را بردارید. (پاک کردن محصول، تاریخچهٔ قیمتش را هم پاک می‌کند.)
- جستجوی بالای سایت در همهٔ محصولات می‌گردد و جستجوی صفحهٔ هر دسته فقط در همان دسته.

## ۱۲. خرید، سفارش‌ها، هزینهٔ ارسال و درگاه پرداخت

### روند خرید مشتری

1. مشتری کالا را به سبد اضافه می‌کند (بیشتر از موجودی قابل افزودن نیست؛ کالای ناموجود اصلاً اضافه نمی‌شود).
2. در صفحهٔ «تسویه حساب»: اگر وارد نشده باشد، شمارهٔ موبایلش را با کد پیامکی تأیید می‌کند (ورود به حساب لازم نیست). سپس نشانی، کد پستی ۱۰ رقمی و روش پرداخت را وارد می‌کند و باید گزینهٔ «تأیید می‌کنم که بالای ۱۸ سال سن دارم.» را بزند.
3. هنگام ثبت، قیمت‌ها و موجودی دوباره بررسی می‌شوند. اگر قیمتی در این فاصله عوض شده باشد، مبلغ جدید به مشتری نشان داده می‌شود و باید دوباره ثبت کند.
4. پرداخت اینترنتی: مشتری به درگاه می‌رود و برمی‌گردد. کارت به کارت: شماره کارت‌ها و مبلغ دقیق را می‌بیند، کد پیگیری (و اگر بخواهد عکس رسید) را ثبت می‌کند و سفارش «در انتظار تأیید پرداخت» می‌شود.
5. **موجودی انبار فقط وقتی کم می‌شود که پرداخت تأیید شود** (پرداخت اینترنتی موفق، یا تأیید کارت به کارت توسط مدیر). اگر سفارشِ تأییدشده لغو شود، موجودی برمی‌گردد.

قیمت‌ها، نام کالاها و نشانی در خود سفارش ذخیره می‌شوند؛ تغییر بعدی قیمت محصولات روی سفارش‌های قبلی اثری ندارد.

مشتری‌ها وضعیت سفارش را در «حساب من» یا در صفحهٔ **پیگیری سفارش** (پایین سایت؛ با شمارهٔ موبایل و شمارهٔ سفارش) می‌بینند. شمارهٔ سفارش یک عدد ۷ رقمی است.

**پیامک‌ها:** هنگام ثبت سفارش، تأیید پرداخت و ارسال (همراه کد رهگیری پست) برای مشتری پیامک فرستاده می‌شود، و با تأیید پرداخت یک پیامک هم برای مدیر ([بخش ۱۳](#۱۳-کد-تخفیف-هدیه-و-پیامک)).

**محدودیت کد ورود:** هر کد ۵ رقمی ۲ دقیقه اعتبار دارد و ۵ بار اشتباه وارد کردن آن را باطل می‌کند. بین دو درخواست کد برای یک شماره دست‌کم ۶۰ ثانیه فاصله لازم است. در هر ساعت برای هر شماره حداکثر ۵ کد و از هر آی‌پی حداکثر ۱۵ کد فرستاده می‌شود (قابل تغییر در `.env`: `OTP_MAX_PER_MOBILE_PER_HOUR` و `OTP_MAX_PER_IP_PER_HOUR`).

### هزینهٔ ارسال (فقط پست)

در **تنظیمات سایت ← هزینهٔ ارسال (پست)** سه خانه هست:

| خانه | پیش‌فرض | توضیح |
|---|---|---|
| هر پلهٔ هزینهٔ ارسال | ۳٬۰۰۰٬۰۰۰ تومان | مبلغ خرید هر پله |
| هزینهٔ ارسال هر پله | ۲۰۰٬۰۰۰ تومان | برای ارسال رایگان صفر بگذارید |
| گرد کردن تعداد پله‌ها | رو به بالا | رو به بالا یا رو به پایین |

هزینهٔ ارسال = تعداد پله‌ها × هزینهٔ هر پله، و تعداد پله‌ها = مبلغ خرید (بعد از تخفیف) ÷ مبلغ هر پله. با تنظیمات پیش‌فرض:

| مبلغ خرید (تومان) | رو به بالا | رو به پایین |
|---|---|---|
| ۱٬۰۰۰٬۰۰۰ | ۲۰۰٬۰۰۰ | رایگان |
| ۳٬۰۰۰٬۰۰۰ | ۲۰۰٬۰۰۰ | ۲۰۰٬۰۰۰ |
| ۳٬۰۰۰٬۰۰۱ | ۴۰۰٬۰۰۰ | ۲۰۰٬۰۰۰ |
| ۷٬۰۰۰٬۰۰۰ | ۶۰۰٬۰۰۰ | ۴۰۰٬۰۰۰ |

هزینهٔ ارسال در سبد خرید و صفحهٔ تسویه حساب جداگانه نشان داده می‌شود.

### راه‌اندازی درگاه پرداخت (زرین‌پال)

> پیش از ثبت‌نام، از پشتیبانی بپرسید که نوع کسب‌وکار و کالاهای شما را تأیید می‌کنند یا نه ([توضیح](#پیش-از-باز-کردن-سایت-برای-فروش)). تا آن موقع کارت به کارت بدون درگاه کار می‌کند.

1. در <https://www.zarinpal.com> حساب بسازید، احراز هویت را کامل کنید و برای دامنهٔ سایت **درگاه پرداخت** بگیرید. نشانی سایت باید با HTTPS باز شود.
2. پس از تأیید درگاه، در پنل زرین‌پال **مرچنت کد** (یک رشتهٔ ۳۶ نویسه‌ای مثل `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`) را کپی کنید.
3. در پنل مدیریت سایت: **تنظیمات سایت ← پرداخت**:
   - «درگاه پرداخت»: زرین‌پال
   - «شناسهٔ پذیرنده (مرچنت کد)»: همان کد
   - «پرداخت اینترنتی فعال باشد»: روشن
   - «حالت آزمایشی درگاه (سندباکس)»: **خاموش**
4. ذخیره کنید. از این لحظه گزینهٔ «پرداخت اینترنتی» در صفحهٔ تسویه حساب دیده می‌شود. تا وقتی مرچنت کد خالی است، این گزینه نشان داده نمی‌شود.
5. یک خرید کوچک واقعی انجام دهید و مطمئن شوید سفارش «پرداخت‌شده، در حال آماده‌سازی» شد.

**آزمایش بدون پول واقعی (سندباکس):** «حالت آزمایشی» را روشن کنید و در «مرچنت کد» هر رشتهٔ ۳۶ نویسه‌ای به شکل بالا بگذارید (مثلاً `00000000-0000-0000-0000-000000000000`). در این حالت پولی جابه‌جا نمی‌شود ولی سفارش «پرداخت‌شده» ثبت می‌شود و موجودی کم می‌شود؛ **پس حتماً بعد از آزمایش آن را خاموش کنید** و سفارش‌های آزمایشی را لغو کنید.

**نکته‌ها:**

- سرور باید بتواند به `payment.zarinpal.com` وصل شود. اگر خطای «شناسهٔ پذیرنده (مرچنت) یا آی‌پی سرور معتبر نیست» دیدید، مرچنت کد را دوباره بررسی کنید؛ اگر درست بود، از پشتیبانی زرین‌پال بپرسید که آی‌پی سرور شما مجاز است یا نه.
- اگر مشتری پول پرداخت کند ولی در همان لحظه موجودی تمام شده باشد، سایت پرداخت را **تأیید نمی‌کند** و زرین‌پال مبلغ را خودکار (معمولاً تا ۷۲ ساعت) به حساب مشتری برمی‌گرداند. به مشتری هم همین پیام نشان داده می‌شود.
- بازگشت چندبارهٔ مشتری از درگاه (مثلاً تازه کردن صفحه) هیچ‌وقت باعث دوبار ثبت پرداخت یا دوبار کم شدن موجودی نمی‌شود.
- اگر مشتری از پرداخت انصراف دهد، سفارش «پرداخت ناموفق» می‌شود و خودش می‌تواند از صفحهٔ سفارش دوباره پرداخت کند.

### کارت به کارت

1. در **تنظیمات سایت**، پایین صفحه، شماره کارت‌ها را با نام صاحب کارت وارد کنید و «فعال» را بزنید.
2. در بخش «پرداخت»، «کارت به کارت فعال باشد» را روشن کنید. (بدون هیچ کارت فعالی، این گزینه به مشتری نشان داده نمی‌شود.)

مشتری بعد از واریز، کد پیگیری و در صورت تمایل عکس رسید (JPG، PNG یا WebP، حداکثر ۵ مگابایت، قابل تغییر با `RECEIPT_MAX_MB` در `.env`) را ثبت می‌کند. عکس رسیدها در جای جداگانه‌ای نگه داشته می‌شوند که از اینترنت قابل دسترسی نیست؛ فقط مدیران وارد‌شده آن‌ها را می‌بینند. تأیید یا رد پرداخت در صفحهٔ همان سفارش انجام می‌شود ([بخش ۱۴](#۱۴-کار-روزانه-با-سفارشها)).

**کارت به کارت بدون درگاه بانکی هم کار می‌کند.** تا وقتی درگاه پرداخت اینترنتی ندارید (یا تأییدش طول می‌کشد)، فقط کارت به کارت را روشن نگه دارید.

> **پشتیبان‌گیری:** عکس رسیدها مثل عکس محصولات جزو پشتیبان خودکار پایگاه داده نیستند. برای کپی دستی:
> `docker compose cp app:/app/data/private ./private-copy`

## ۱۳. کد تخفیف، هدیه و پیامک

### کد تخفیف

در پنل مدیریت: **سفارش‌ها ← کدهای تخفیف ← افزودن**.

| خانه | توضیح |
|---|---|
| کد | حروف انگلیسی، عدد، `-` یا `_` (۳ تا ۳۰ نویسه). بزرگی و کوچکی حروف فرقی ندارد: `sale` و `SALE` یکی هستند |
| نوع تخفیف | «درصدی» (مقدار ۱ تا ۱۰۰) یا «مبلغ ثابت» (مقدار به تومان) |
| سقف مبلغ تخفیف | فقط برای درصدی؛ مثلاً ۱۰٪ با سقف ۵۰۰٬۰۰۰ تومان. خالی یعنی بدون سقف |
| حداقل مبلغ خرید | جمع کالاها (بدون هزینهٔ ارسال) باید دست‌کم این مقدار باشد |
| سقف کل دفعات استفاده | مثلاً ۱۰۰ یعنی فقط ۱۰۰ سفارش می‌توانند از آن استفاده کنند. خالی یعنی بی‌نهایت |
| سقف استفادهٔ هر مشتری | پیش‌فرض ۱. بر اساس حساب کاربری **یا** شمارهٔ موبایل تأییدشده شمرده می‌شود (مهمان‌ها هم شامل می‌شوند) |
| شروع و پایان اعتبار | خالی یعنی از همین حالا / بدون پایان |

- تخفیف فقط روی **جمع کالاها** حساب می‌شود، نه هزینهٔ ارسال. هزینهٔ ارسال و تعداد هدیه‌ها از مبلغ **بعد از تخفیف** حساب می‌شوند.
- مشتری کد را در سبد خرید یا صفحهٔ تسویه حساب وارد می‌کند. اگر کد قابل استفاده نباشد، دلیلش به فارسی نشان داده می‌شود (مثلاً «این کد تخفیف برای خرید دست‌کم ۲٬۰۰۰٬۰۰۰ تومان است؛ ۳۰۰٬۰۰۰ تومان دیگر کالا به سبد اضافه کنید.»).
- یک «استفاده» وقتی شمرده می‌شود که **پرداخت سفارش تأیید شود**؛ اگر آن سفارش لغو شود، استفاده برمی‌گردد. ستون «استفاده‌شده» در فهرست کدها همین عدد است.
- برای از کار انداختن یک کد، تیک «فعال» را بردارید (پاک کردن کد هم ممکن است، ولی سفارش‌های قبلی فقط متن کد را نگه می‌دارند).

### هدیه

1. در **تنظیمات سایت ← هدیه**: «هدیه فعال باشد» و «مبلغ خرید برای هر هدیه» (پیش‌فرض ۳٬۰۰۰٬۰۰۰ تومان).
2. در **سفارش‌ها ← کالاهای هدیه**: کالاهایی که مشتری می‌تواند به‌عنوان هدیه انتخاب کند و **موجودی هدیهٔ** هر کدام. فرمان `seed_products` در ابتدا «دستگاه خشابی» و همهٔ توتون‌ها را با موجودی هدیهٔ ۰ اضافه می‌کند؛ موجودی هدیه را خودتان بگذارید.

قاعده: تعداد هدیه = جمع کالاها بعد از تخفیف ÷ مبلغ هر هدیه، رو به پایین (هزینهٔ ارسال حساب نمی‌شود). مثلاً با ۳ میلیون: خرید ۲٬۹۹۹٬۹۹۹ تومانی بدون هدیه، ۳ میلیونی ۱ هدیه، ۷ میلیونی ۲ هدیه. اگر تخفیف مبلغ را زیر یک پله ببرد، تعداد هدیه هم کم می‌شود.

- در سبد خرید پیامی مثل «با ۵۰۰٬۰۰۰ تومان خرید بیشتر یک هدیه می‌گیرید.» دیده می‌شود (فقط وقتی هدیه فعال است و دست‌کم یک کالای هدیه موجود باشد).
- در تسویه حساب، مشتری هر هدیه را از فهرست انتخاب می‌کند؛ یک کالا را می‌تواند چند بار انتخاب کند، تا جایی که موجودی هدیه و موجودی خود کالا اجازه دهد. همه چیز دوباره در سرور بررسی می‌شود.
- هدیه‌ها با قیمت صفر و برچسب «هدیه» در سفارش، صفحهٔ سفارش مشتری و پیامک مدیر می‌آیند.
- با تأیید پرداخت، هم موجودی کالا و هم موجودی هدیه کم می‌شود و با لغو سفارش هر دو برمی‌گردند. اگر پیش از تأیید پرداخت موجودی هدیه تمام شده باشد، با سفارش مثل «کالای ناموجود» رفتار می‌شود (پرداخت اینترنتی تأیید نمی‌شود و پول خودکار برمی‌گردد؛ کارت به کارت تا اصلاح موجودی قابل تأیید نیست).

### پیامک

تا وقتی «کلید API سرویس پیامک» خالی است، سایت در **حالت آزمایشی پیامک** کار می‌کند: هیچ پیامکی فرستاده نمی‌شود، ولی همه چیز (ثبت سفارش، پرداخت، …) کار می‌کند و متن هر پیامک در **اعلان‌ها ← گزارش پیامک‌ها** و در گزارش برنامه ثبت می‌شود:

```bash
docker compose logs --tail=50 app
```

> در این حالت مشتری‌ها کد ورود را دریافت نمی‌کنند، پس پیش از باز کردن سایت برای فروش، سرویس پیامک را راه بیندازید. (کد ورود فقط در گزارش برنامه دیده می‌شود؛ در «گزارش پیامک‌ها» پس از ارسال با • پوشانده می‌شود.)

#### راه‌اندازی کاوه‌نگار

> پیش از ثبت‌نام، از پشتیبانی سرویس پیامک بپرسید که نوع کسب‌وکار شما را تأیید می‌کنند یا نه ([توضیح](#پیش-از-باز-کردن-سایت-برای-فروش)).

1. در <https://kavenegar.com> ثبت‌نام کنید، احراز هویت را کامل کنید و حساب را شارژ کنید.
2. در پنل کاوه‌نگار، در بخش تنظیمات حساب، «کلید API» (API Key) را پیدا و کپی کنید.
3. در همان پنل، شمارهٔ خط ارسال خود را ببینید (مثلاً `10004346` یا خط اختصاصی). اگر خط اختصاصی ندارید، این خانه را در سایت خالی بگذارید تا خط پیش‌فرض حساب استفاده شود.
4. در پنل مدیریت سایت: **تنظیمات سایت ← پیامک**:
   - «سرویس پیامک»: کاوه‌نگار
   - «کلید API سرویس پیامک»: همان کلید
   - «شمارهٔ فرستنده (خط پیامک)»: شمارهٔ خط (یا خالی)
5. ذخیره کنید و با شمارهٔ خودتان از صفحهٔ ورود سایت یک کد بگیرید. در **اعلان‌ها ← گزارش پیامک‌ها** وضعیت باید «ارسال‌شده» باشد.

اگر وضعیت «ناموفق» یا «در انتظار تلاش دوباره» بود، روی ردیف بزنید و خانه‌های «خطا» و «پاسخ سرویس» را ببینید. رایج‌ترین‌ها: «کلید API کاوه‌نگار معتبر نیست» (کلید را دوباره کپی کنید)، «شمارهٔ فرستنده معتبر نیست» (خانهٔ فرستنده را خالی کنید یا خط درست را بنویسید)، «اعتبار حساب کافی نیست» (حساب را شارژ کنید). سرور باید به `api.kavenegar.com` دسترسی داشته باشد.

**ارسال و تلاش دوباره:** پیامک‌ها در صف پس‌زمینه (کانتینر `worker`) فرستاده می‌شوند، پس ثبت سفارش هیچ‌وقت منتظر سرویس پیامک نمی‌ماند و خطای پیامک هرگز جلوی خرید را نمی‌گیرد. اگر ارسال ناموفق باشد، پس از ۱، ۵، ۱۵ و ۶۰ دقیقه دوباره تلاش می‌شود (روی‌هم ۵ تلاش)؛ خطاهایی که با تکرار درست نمی‌شوند (مثل کلید یا شمارهٔ نادرست) فوراً «ناموفق» می‌شوند. پیامک طولانی چندبخشی فرستاده می‌شود و هیچ‌وقت کوتاه نمی‌شود (ستون «تعداد بخش»؛ هر بخش فارسی ۶۷ تا ۷۰ نویسه است و جدا هزینه دارد).

> اگر کانتینر `worker` خاموش باشد، پیامک‌ها در صف می‌مانند و پس از روشن شدن آن فرستاده می‌شوند: `docker compose ps` و `docker compose logs --tail=50 worker`.

#### متن پیامک‌ها

در **اعلان‌ها ← متن‌های پیامک** پنج متن قابل ویرایش است: کد تأیید، ثبت سفارش، تأیید پرداخت، ارسال سفارش (با کد رهگیری) و سفارش جدید (به مدیر). متغیرها داخل آکولاد نوشته می‌شوند، مثل `{order_number}`؛ فهرست متغیرهای مجاز هر متن در همان صفحه آمده و متغیر نادرست ذخیره نمی‌شود.

#### پیامک سفارش جدید به مدیر

در **تنظیمات سایت ← پیامک مدیر** شمارهٔ یک یا چند مدیر را (هر کدام در یک خط) بنویسید و «پیامک سفارش جدید به مدیر» را روشن بگذارید. برای هر سفارش **فقط یک بار**، وقتی پرداخت آن تأیید می‌شود، پیامکی مثل این فرستاده می‌شود:

```
پوکه پرستون 16
آریزونا 3
شمزین 2 (هدیه)
علی رضایی
09121111111
1234567890
تهران، تهران، خیابان آزادی، پلاک ۱
```

هر خط یک کالا (نام کوتاه و تعداد؛ هدیه‌ها با «(هدیه)»)، سپس نام گیرنده، موبایل، کد پستی و نشانی کامل. اگر پیامک نرسید، در صفحهٔ سفارش دکمهٔ **«ارسال مجدد پیامک ادمین»** را بزنید (این دکمه حتی وقتی پیامک خودکار مدیر خاموش است کار می‌کند).

#### سرویس دیگر (ملی‌پیامک، SMS.ir، …)

فعلاً فقط کاوه‌نگار آماده است. افزودن سرویس دیگر کار یک برنامه‌نویس است و فقط یک فایل لازم دارد (بخش «برای برنامه‌نویس‌ها» را ببینید)؛ بعد از آن سرویس جدید در فهرست «سرویس پیامک» دیده می‌شود.

## ۱۴. کار روزانه با سفارش‌ها

همه در **فروش ← سفارش‌ها**. سفارش‌ها را در پنل نمی‌توان ساخت یا پاک کرد (سفارش فقط از سایت ثبت می‌شود و به‌جای پاک کردن، «لغو» می‌شود تا موجودی درست بماند).

### پیدا کردن سفارش

- **جستجو** (بالای فهرست): شمارهٔ سفارش، موبایل، نام گیرنده یا کد رهگیری؛ رقم فارسی یا انگلیسی فرقی ندارد.
- **فیلترها** (ستون کناری): وضعیت، روش پرداخت، و تاریخ ثبت (امروز، این هفته، این ماه، ماه گذشته، ۳۰ روز اخیر؛ به تقویم شمسی).
- از پیشخوان، روی کادر «در انتظار تأیید کارت به کارت» یا «آمادهٔ ارسال» بزنید تا همان سفارش‌ها فیلتر شوند.

### روند هر سفارش

| وضعیت | یعنی | کار شما |
|---|---|---|
| در انتظار پرداخت | مشتری هنوز پرداخت نکرده | هیچ (یا لغو) |
| در انتظار تأیید پرداخت | مشتری کارت به کارت کرده و کد پیگیری داده | واریز را در حساب بانکی ببینید، سپس **«تأیید پرداخت کارت به کارت»** یا **«رد پرداخت»** |
| پرداخت‌شده، در حال آماده‌سازی | پرداخت تأیید شده و موجودی کم شده | بسته را آماده کنید، **برگهٔ بسته‌بندی** را چاپ کنید، به پست بدهید، **کد رهگیری** را وارد و «ثبت ارسال» را بزنید |
| ارسال‌شده | مشتری پیامک کد رهگیری را گرفته | پس از رسیدن بسته، **«ثبت تحویل‌شده»** |
| تحویل‌شده / لغوشده / پرداخت ناموفق | پایان | — |

در صفحهٔ هر سفارش این‌ها را می‌بینید: اقلام (هدیه‌ها با برچسب «هدیه»)، تخفیف و هزینهٔ ارسال، گیرنده و نشانی، پرداخت‌ها (کد پیگیری کارت به کارت یا کد پیگیری بانکی، و **عکس رسید**؛ روی عکس بزنید تا بزرگ شود) و **تاریخچهٔ وضعیت** (چه کسی، چه زمانی، چه تغییری داد).

- **تأیید کارت به کارت:** مبلغ و کد پیگیری را با حساب بانکی مقایسه کنید. با تأیید، موجودی کالاها و هدیه‌ها کم می‌شود و برای مشتری و مدیر پیامک می‌رود. اگر در این فاصله موجودی کالایی تمام شده باشد، تأیید انجام نمی‌شود و پیام «موجودی کافی نیست» می‌آید؛ موجودی را درست کنید یا سفارش را رد کنید.
- **رد پرداخت:** سفارش لغو می‌شود. می‌توانید دلیل را بنویسید (در تاریخچه می‌ماند).
- **ثبت ارسال:** کد رهگیری پست را بنویسید (رقم فارسی هم قبول است). مشتری پیامکی با کد رهگیری می‌گیرد.
- **لغو سفارش:** تا پیش از ارسال ممکن است. اگر سفارش پرداخت‌شده بود، موجودی کالاها، موجودی هدیه‌ها و استفاده از کد تخفیف **خودکار برمی‌گردد**؛ ولی **بازگرداندن پول** مشتری را خودتان انجام دهید.
- **ارسال مجدد پیامک ادمین:** پیامک مشخصات سفارش را دوباره برای همهٔ شماره‌های مدیر می‌فرستد.

### چاپ برگهٔ بسته‌بندی و برچسب نشانی

در صفحهٔ سفارش **«چاپ برگهٔ بسته‌بندی»** را بزنید (برای چند سفارش با هم: در فهرست سفارش‌ها تیک بزنید و از «عملیات» گزینهٔ **«چاپ برگهٔ بسته‌بندی سفارش‌های انتخاب‌شده»**). هر سفارش یک صفحه است (اندازهٔ A5): بالای صفحه **برچسب نشانی** (گیرنده، نشانی، کد پستی، موبایل، فرستنده و شمارهٔ سفارش) که می‌توانید ببُرید و روی بسته بچسبانید، و پایین آن **فهرست اقلام با هدیه‌ها** و یک خانهٔ تیک برای هر قلم. دکمهٔ «چاپ» را بزنید؛ در پنجرهٔ چاپ مرورگر می‌توانید کاغذ A4 هم انتخاب کنید.

### خروجی اکسل

در فهرست سفارش‌ها **«خروجی اکسل (همین فهرست)»** همهٔ سفارش‌هایی را که با جستجو و فیلتر فعلی دیده می‌شوند (همهٔ صفحه‌ها) در یک فایل `xlsx` می‌دهد؛ مثلاً اول فیلتر «این ماه» و «ارسال‌شده» را بزنید. برای سفارش‌های دلخواه: تیک بزنید و از «عملیات» گزینهٔ **«خروجی اکسل سفارش‌های انتخاب‌شده»**. ستون‌ها: شماره، تاریخ‌ها (شمسی)، وضعیت، روش پرداخت، موبایل‌ها، نشانی، اقلام (با هدیه‌ها)، مبلغ‌ها به تومان، کد تخفیف و کد رهگیری.

### مشتریان

**فروش ← مشتریان** همهٔ کسانی را که با موبایل ثبت‌نام کرده‌اند نشان می‌دهد، با تعداد سفارش‌های پرداخت‌شده، جمع خرید و تاریخ آخرین سفارش (قابل مرتب‌سازی با کلیک روی عنوان ستون). در صفحهٔ هر مشتری **تاریخچهٔ همهٔ سفارش‌هایش** (از جمله سفارش‌هایی که پیش از ثبت‌نام، به‌صورت مهمان با همان موبایل ثبت کرده) و نشانی‌های ذخیره‌شده‌اش دیده می‌شود. برای بستن حساب یک مشتری، تیک «فعال» را بردارید. خریدهای مهمان (بدون ثبت‌نام) فقط در «سفارش‌ها» هستند (با موبایل جستجو کنید).

## ۱۵. امنیت پنل مدیریت

- **نشانی پنل** همان `ADMIN_URL` است و `/admin/` وجود ندارد. آن را به کسی جز مدیران ندهید.
- **قفل ورود:** پس از ۵ بار رمز (یا کد دومرحله‌ای) نادرست، ورود به پنل از همان آی‌پی **۱ ساعت** بسته می‌شود (قابل تغییر با `AXES_FAILURE_LIMIT` و `AXES_COOLOFF_HOURS` در `.env`). فهرست آی‌پی‌های قفل‌شده در **کاربران و امنیت ← قفل‌های ورود به پنل** است؛ با «باز کردن قفل ردیف‌های انتخاب‌شده» آزادشان کنید. اگر خودتان قفل شده‌اید: `docker compose exec app python manage.py axes_reset`
- **ورود دومرحله‌ای (بسیار توصیه می‌شود):** بالای پنل روی **«ورود دومرحله‌ای»** بزنید، با برنامهٔ Google Authenticator یا Microsoft Authenticator تصویر QR را اسکن کنید و کد ۶ رقمی را وارد کنید. از آن پس، هنگام ورود، کد برنامه را هم در خانهٔ «کد ورود دومرحله‌ای» می‌نویسید. هر مدیر برای خودش روشن می‌کند؛ ستون «ورود دومرحله‌ای» در فهرست کاربران نشان می‌دهد چه کسی روشن کرده است. **ساعت گوشی باید درست باشد** (تنظیم خودکار ساعت). اگر گوشی گم شد: مدیر دیگری در **کاربران و امنیت ← ورود دومرحله‌ای مدیران** ردیف شما را پاک می‌کند، یا روی سرور: `docker compose exec app python manage.py disable_2fa <موبایل>`
- **رمز قوی** بگذارید (دست‌کم ۱۲ نویسه). رمز را عوض کنید: بالای پنل «تغییر گذرواژه».
- هر مدیری که دیگر کار نمی‌کند: در «کاربران و مدیران» تیک «فعال» یا «وضعیت کارمندی» او را بردارید.
- سایت فقط با HTTPS باز می‌شود، کوکی‌ها فقط روی HTTPS فرستاده می‌شوند، و فقط تصویرهای JPG/PNG/WebP (حداکثر ۵ مگابایت) پذیرفته می‌شوند.

## ۱۶. سئو و محتوا

همهٔ متن‌های سایت (مقاله‌ها، معرفی دسته‌ها، پرسش‌های متداول، توضیح محصولات) را **خودتان** می‌نویسید؛ سایت هیچ متنی خودکار تولید نمی‌کند. فقط عنوان و توضیح سئو، اگر خالی بمانند، از نام و متن خود صفحه ساخته می‌شوند.

### پیش از هر چیز: تنظیمات سئو

در **تنظیمات ← تنظیمات سایت ← بخش «سئو و شبکه‌های اجتماعی»**:

- **معرفی کوتاه و بی‌طرف سایت:** یکی دو جملهٔ واقعی (مثلاً «فروشگاه اینترنتی توتون و لوازم جانبی، ارسال با پست به سراسر ایران»). توضیح پیش‌فرض صفحه‌ها و فایل `llms.txt` از همین ساخته می‌شود.
- **نام رسمی کسب‌وکار، لوگو، تلفن، شبکه‌های اجتماعی** (هر نشانی در یک خط، با `https://`): برای کارت اطلاعات کسب‌وکار در نتایج گوگل.
- **تصویر پیش‌فرض اشتراک‌گذاری** (۱۲۰۰×۶۳۰): وقتی لینک صفحه‌ای که تصویر ندارد در تلگرام و واتساپ فرستاده می‌شود.
- **هشدار سلامت:** پایین همهٔ صفحه‌ها و در صفحهٔ هر محصول نمایش داده می‌شود (پیش‌فرض: «استعمال دخانیات برای سلامت مضر است»).
- **اجازه به خزنده‌های هوش مصنوعی** (GPTBot، ClaudeBot، PerplexityBot، Google-Extended، CCBot): پیش‌فرض روشن است. خاموش کنید، در `robots.txt` مسدود می‌شوند. موتورهای جستجوی معمولی (گوگل، بینگ) تأثیری نمی‌پذیرند.
- **کد آمار بازدید** (اختیاری): فقط کدی که منبعش را می‌شناسید. سیاست امنیتی سایت (CSP) اسکریپت‌های دامنه‌های دیگر را مسدود می‌کند؛ سرویس آماری که از دامنهٔ دیگری بارگذاری می‌شود کار نمی‌کند مگر برنامه‌نویس آن دامنه را به `CONTENT_SECURITY_POLICY` اضافه کند.

### نوشتن یک مقاله

1. **مقاله‌ها ← مقاله‌ها ← افزودن**. عنوان را بنویسید؛ نشانی (slug) اگر خالی بماند از عنوان ساخته می‌شود.
2. **پاسخ کوتاه:** ۲ تا ۳ جمله که مستقیم به پرسش اصلی مقاله جواب می‌دهد. در کادر برجستهٔ بالای مقاله می‌آید و موتورهای جستجو و دستیارهای هوش مصنوعی معمولاً همین را نقل می‌کنند.
3. **متن مقاله:** در ویرایشگر، تیترها را با «عنوان ۲» (Heading 2) و زیرتیترها را با «عنوان ۳» بسازید؛ **فهرست مطالب خودکار** از همین‌ها ساخته می‌شود. «عنوان ۱» نزنید (عنوان مقاله خودش عنوان اصلی است). هر کد ناامن (اسکریپت و …) هنگام ذخیره حذف می‌شود.
4. **تصویر شاخص** و **متن جایگزین (alt)** آن: یک جملهٔ کوتاه که بگوید در تصویر چه دیده می‌شود.
5. دسته، برچسب‌ها، نام نویسنده، **محصولات مرتبط** و **مقاله‌های مرتبط** را انتخاب کنید (پایین مقاله و در صفحهٔ آن محصولات لینک می‌شوند).
6. **پرسش‌های متداول** (پایین فرم): هر پرسش و پاسخ در یک ردیف. در صفحه و در دادهٔ ساختاریافته (FAQPage) می‌آیند.
7. با وضعیت **پیش‌نویس** ذخیره کنید و با **«مشاهده در سایت»** پیش‌نمایش ببینید (پیش‌نویس را فقط مدیران می‌بینند). کادر **«چک‌لیست محتوا»** بالای فرم کمبودها را یادآوری می‌کند (پاسخ کوتاه، توضیح متا، تصویر شاخص و alt آن، پرسش متداول)؛ مانع ذخیره نمی‌شود.
8. وضعیت را **منتشرشده** کنید. «تاریخ انتشار» اگر خالی باشد همان لحظه ثبت می‌شود؛ تاریخ آینده یعنی انتشار زمان‌بندی‌شده. برای چند مقاله با هم: در فهرست مقاله‌ها تیک بزنید و عمل «انتشار» یا «برگرداندن به پیش‌نویس» را اجرا کنید.
9. «آخرین به‌روزرسانی» با هر ذخیره خودکار عوض می‌شود. مقاله‌های قدیمی را به‌روز نگه دارید.

### پر کردن فیلدهای سئو

محصول، دسته، صفحهٔ ثابت، مقاله و دستهٔ مقاله هر کدام بخش جمع‌شدهٔ **«سئو (اختیاری)»** دارند:

- **عنوان سئو:** حدود ۶۰ نویسه؛ شمارنده زیر خانه نشان می‌دهد. خالی = «نام | نام سایت».
- **توضیح متا:** ۷۰ تا ۱۶۰ نویسه؛ جمله‌ای که در نتایج گوگل زیر عنوان می‌آید. خالی = ابتدای متن خود صفحه.
- **نشانی canonical دلخواه:** معمولاً خالی بگذارید. فقط وقتی این صفحه کپی صفحهٔ دیگری است، نشانی آن صفحه را بنویسید.
- **noindex:** صفحه از نتایج جستجو و نقشهٔ سایت بیرون می‌رود (مثلاً برای صفحه‌های کم‌محتوا).
- **متن جایگزین (alt)** هر تصویر محصول، تصویر دسته و بنر را پر کنید.
- **مشخصات فنی** محصول (کشور سازنده، نوع، وزن، …) جدولی در صفحهٔ محصول می‌شود؛ **برند** و **کد کالا (SKU)** هم در دادهٔ ساختاریافته می‌آیند.
- **دسته‌ها:** «متن معرفی بالای صفحه» و «پرسش‌های متداول» را برای دسته‌های اصلی بنویسید.

**تغییر نشانی (slug):** اگر نشانی یک محصول، دسته، صفحه یا مقاله را عوض کنید، نشانی قدیمی خودکار با **ریدایرکت ۳۰۱** به نشانی جدید می‌رود (لینک‌ها و رتبهٔ قبلی از دست نمی‌رود). ریدایرکت‌های دستی (مثلاً از نشانی‌های سایت قبلی‌تان) را در **محتوای سایت ← ریدایرکت‌ها** اضافه کنید: نشانی قدیمی مثل `/old-page/` و نشانی جدید مثل `/p/نام-محصول/`.

### ثبت سایت در Google Search Console و Bing

1. به [search.google.com/search-console](https://search.google.com/search-console) بروید، **Add property ← URL prefix** و نشانی کامل سایت (`https://دامنه/`) را وارد کنید.
2. روش تأیید **HTML tag** را انتخاب کنید. از تگ `<meta name="google-site-verification" content="…">` فقط مقدار داخل `content` را کپی کنید و در **تنظیمات سایت ← کد تأیید Google Search Console** بگذارید و ذخیره کنید؛ سپس در Search Console دکمهٔ **Verify** را بزنید.
3. در Search Console از منوی **Sitemaps** نشانی `sitemap.xml` را وارد و **Submit** کنید (`https://دامنه/sitemap.xml`).
4. برای بینگ: [bing.com/webmasters](https://www.bing.com/webmasters) ← افزودن سایت. ساده‌ترین راه **Import from Google Search Console** است. وگرنه روش **HTML Meta Tag** را انتخاب کنید، مقدار `content` تگ `msvalidate.01` را در **کد تأیید Bing Webmaster** بگذارید، تأیید کنید و در بخش Sitemaps همان `https://دامنه/sitemap.xml` را ثبت کنید.
5. بعد از چند روز، گزارش‌های **Pages** (صفحه‌های فهرست‌شده) و **Enhancements** (محصولات، پرسش‌های متداول، مسیر صفحه) را ببینید. برای بررسی یک صفحه از [Rich Results Test](https://search.google.com/test/rich-results) استفاده کنید.

فایل‌های خودکار: `https://دامنه/sitemap.xml` (نقشهٔ سایت؛ محصولات، دسته‌ها، مقاله‌ها و صفحه‌ها)، `https://دامنه/robots.txt` (سبد خرید، تسویه، حساب کاربری، پرداخت، جستجو و نشانی‌های مرتب‌سازی را از خزنده‌ها پنهان می‌کند؛ نشانی پنل مدیریت عمداً در آن نیامده تا فاش نشود، و صفحه‌های پنل خودشان noindex هستند) و `https://دامنه/llms.txt` (خلاصهٔ ساختاریافتهٔ سایت برای دستیارهای هوش مصنوعی). نیازی به ویرایش دستی آن‌ها نیست.

**پنجرهٔ تأیید سن** فقط روی صفحه نمایش داده می‌شود و محتوای صفحه برای همه (از جمله گوگل) کامل فرستاده می‌شود؛ پس مانع فهرست شدن صفحه‌ها نیست.

### بررسی نظرهای مشتریان

- فقط مشتریانِ واردشده (با کد پیامکی) می‌توانند برای هر محصول **یک** نظر و امتیاز ۱ تا ۵ ثبت کنند. نظرهای دارای لینک یا شمارهٔ تلفن پذیرفته نمی‌شوند.
- **همهٔ نظرها ابتدا «در انتظار بررسی» هستند** و تا تأیید نکنید در سایت دیده نمی‌شوند. تعداد نظرهای در انتظار روی **داشبورد** پنل نمایش داده می‌شود.
- **نظرهای مشتریان ← نظرهای مشتریان**: با فیلتر «وضعیت = در انتظار بررسی» شروع کنید، نظرها را تیک بزنید و عمل **«تأیید»** یا **«رد»** را اجرا کنید. برای پاسخ، نظر را باز کنید و «پاسخ فروشگاه» را بنویسید؛ زیر همان نظر در سایت نمایش داده می‌شود.
- نشان **«خرید تأییدشده»** خودکار است: وقتی آن مشتری سفارش پرداخت‌شده، ارسال‌شده یا تحویل‌شده‌ای شامل همان محصول داشته باشد.
- میانگین امتیاز و تعداد نظرها فقط از نظرهای **تأییدشده** حساب می‌شود و همان در نتایج گوگل (ستاره‌ها) نشان داده می‌شود. نظر ننوشته یا جعلی وارد نکنید؛ هم خلاف قوانین گوگل است و هم اعتماد مشتری را از بین می‌برد. نظرهای منفی واقعی را رد نکنید؛ به آن‌ها پاسخ دهید.

## پیش از باز کردن سایت برای فروش

> **مهم:** درگاه پرداخت اینترنتی (زرین‌پال یا هر درگاه دیگر) و سرویس پیامک (کاوه‌نگار یا هر سرویس دیگر) باید **نوع کسب‌وکار شما را بپذیرند و تأیید کنند**. بسیاری از درگاه‌ها و سرویس‌های پیامک برای برخی دسته‌کالاها (از جمله دخانیات و لوازم آن) مجوز خاص می‌خواهند یا اصلاً درگاه نمی‌دهند. پیش از ثبت‌نام و پرداخت هزینه، از پشتیبانی هر کدام بپرسید که فروش این کالاها را می‌پذیرند یا نه، و پیش از فروش واقعی تأیید کتبی بگیرید. ممکن است پیامک‌هایی با برخی کلمات هم فیلتر شوند؛ متن پیامک‌ها را ساده و بدون نام کالا نگه دارید.

## فرض‌ها (Assumptions)

- **Admin theme:** the stock Django admin is used and styled with brand colours (Django already ships full RTL and Persian translations). django-unfold was not used, to avoid a dependency whose RTL support is less mature.
- **Jalali admin dates:** `django-jalali-date` provides Jalali pickers and Jalali list columns while models keep standard `DateField`/`DateTimeField`, so the ORM stays portable.
- **Rich text:** StaticPage bodies use TinyMCE (bundled, self-hosted via django-tinymce). HTML is sanitised with `nh3` on save.
- **Thousands separator:** prices use the Persian separator `٬` (U+066C), e.g. `۱٬۲۵۰٬۰۰۰ تومان`. Prices are rounded to whole Toman.
- **Age gate:** without the cookie the page is rendered but marked `inert` (not clickable or focusable) under a full-screen dialog. Confirming is a normal form POST, so it works without JavaScript. "Leave" goes to `AGE_GATE_EXIT_URL` (Google by default). The admin and `/health` are not gated.
- **Maintenance mode:** staff users, the admin, `/health`, static and media files bypass it. Visitors get HTTP 503 with `Retry-After`.
- **Placeholders:** none left in the storefront; `core.views.coming_soon` is no longer routed but kept.
- **Custom user model** (`accounts.User`) is created now, because switching user models after launch is painful.
- **Backups:** made with SQLite's online backup API (same mechanism as the `.backup` CLI command) by the django-q2 worker at 03:30 Tehran time, with an integrity check. Only the database is backed up automatically; media copying is documented above.
- **Worker health:** the worker touches `/tmp/worker-heartbeat` every 5 minutes and the Docker healthcheck checks the file's age.
- **Static files** are served by WhiteNoise (hashed, compressed); **media** is served directly by Caddy.
- **Domain:** only the bare domain (`DOMAIN`) is configured in Caddy; `www.` is not.
- **HSTS** is 30 days, without `includeSubDomains`/`preload` (hard to undo for a beginner); the corresponding Django deploy-check warnings are silenced on purpose.
- **Logs:** errors go to `/app/data/logs/errors.log` (5 MB × 5 rotating files) plus container stdout. The logs directory has its own Docker volume.
- **Font:** Vazirmatn v33.003 variable font (OFL licence, in `static/fonts/vazirmatn/`).
- **Price log on every path:** `Product.save()` compares against the stored price, and `ProductQuerySet.update()` (which `bulk_update()` also goes through) logs the rows it changes, so admin edits, list edits, Excel import and bulk actions are all covered. The user comes from a request-scoped context variable (`catalog.audit.ActingUserMiddleware`); outside a request use `with acting_as(user):`. Raw SQL is not covered.
- **Stock locking:** `reserve()` uses `transaction.atomic()` + `select_for_update()` (effective on PostgreSQL). SQLite ignores `select_for_update`, but this project opens transactions with `BEGIN IMMEDIATE`, which serialises writers; the decrement is also conditional (`stock >= qty`) and the column has a `CHECK (stock >= 0)` constraint.
- **Excel import** updates price and stock only, matched by «شناسه»; it never creates or deletes products. Rows are saved one by one (no bulk mode) so each price change is logged. The preview is a rolled-back dry run.
- **Images** are re-encoded on upload: EXIF rotation applied, longest side ≤ 1400 px, WebP quality 82, metadata stripped. Only JPEG/PNG/WebP up to `PRODUCT_IMAGE_MAX_MB` (default 5) are accepted. Files are deleted when their image row is deleted.
- **Slugs:** categories use English slugs (`tobacco`, `accessories`, `machines`, …); products get Persian slugs from their name (ZWNJ becomes `-`), e.g. `/p/دستگاه-زیگ-زاگ-طلایی-ترکیه-ای/`.
- **Search** is a simple `icontains` on name, short name and description; Arabic «ي/ك» are normalised to Persian «ی/ک». The header search now uses it across all products.
- **Seed short names:** long accessory names got a shorter `short_name` (e.g. «پوکه ۲۰۰ نخی مارک مک سایز کینگ» → «پوکه مک»); all others equal the name. «جعبه توتون»، «جعبه سیگار» and «جاسیگاری فندک‌خور» are in «سایر».
- **User model migration:** `username` was renamed to `mobile` (not dropped) and first/last name merged into `name`, so an existing admin such as `admin` keeps signing in with that value until a mobile is set. New superusers come from `DJANGO_SUPERUSER_MOBILE` (`DJANGO_SUPERUSER_USERNAME` is still read as a fallback). Staff sign in to the admin with mobile + password; customers have no password (SMS code only).
- **OTP:** codes are stored as HMAC-SHA256 keyed with `SECRET_KEY`. Rate limits are counted from the `OTPCode` table (shared by all gunicorn workers), not from a cache. Login and checkout codes are separate purposes; the 60-second cooldown is per mobile across purposes. In SMS console mode (no API key) the codes appear in the container logs; `SMSLog` masks them once a message is finished.
- **Visitor IP:** in production the last `X-Forwarded-For` entry is used (the address Caddy saw; Caddy overwrites the header from clients), see `core.utils.client_ip`.
- **Guest verification** lasts for the browser session. A guest's recipient mobile is the verified mobile; signed-in users may enter a different recipient mobile. Guest orders are reachable from the browser that placed them (order numbers kept in the session) and from the tracking page; after signing in with the same mobile they also appear in the user panel.
- **Stock and online payments:** stock is reserved in a short transaction right *before* the gateway verify call and released if verification fails, so money is never captured for items that sold out meanwhile (Zarinpal refunds unverified payments). The verify call runs outside any transaction so it never holds the SQLite write lock. A payment stuck in "verifying" is verified again by a callback arriving 60 s later.
- **Status flow:** pending_payment → awaiting_approval (card) → paid_processing → shipped → delivered; failed → pending_payment (retry); cancel is allowed until shipped. Rejecting a card-to-card payment cancels the order. Invalid transitions raise `orders.models.InvalidTransition`. The order_registered SMS is sent when the order is created, for both payment methods.
- **Order numbers** are 7 random digits (not sequential).
- **Shipping rounding** applies to the subtotal after discount; a 0 subtotal always means 0 shipping. "Floor" means orders below one step ship free.
- **Receipts** are validated like product images (JPEG/PNG/WebP, size limit) and stored unmodified in `PRIVATE_MEDIA_ROOT` (`/app/data/private`, own Docker volume `private`). Staff view them at `/payments/receipt/<id>/`.
- **Saved addresses:** at most 10 per user; "save this address" at checkout skips exact duplicates.
- **Gifts** are ordinary `OrderItem`s with `is_gift=True` and `unit_price=0`; the order page, packing slip, Excel export and admin SMS list them from `order.items`.
- **Discount codes** are stored upper-case (`normalize_code`: Persian digits → Latin, spaces removed) with a `UNIQUE(LOWER(code))` constraint. Allowed characters: `A–Z 0–9 - _`. Percent discounts are rounded down to whole Toman.
- **Discount usage** is a counter (`DiscountCode.used_count`) plus `Order.discount_counted`, changed on confirmation (`confirm_payment`/`approve`) and on release (cancel/reject/fail). The limits are checked when the code is applied and again inside the `create_order` transaction; an order that was already placed keeps its discount even if, by the time its payment is confirmed, other orders have filled the total limit (the customer saw and agreed to that total).
- **Per-customer limit** counts confirmed orders of the same account **or** the same order mobile (guests: the OTP-verified mobile). While a guest has not verified a mobile, the code is accepted in the cart and checked again at checkout. `per_user_limit` defaults to 1.
- **Session code:** the applied code stays in the session even when it stops being valid (e.g. the cart drops below the minimum), shows the reason and gives no discount; checkout is blocked until the customer removes it, so nobody pays full price thinking a code was applied.
- **Gift slots:** the customer gets one select per earned gift, all required, capped by what the pool can still supply (`min(gift_stock, product stock − paid quantity of that product)` summed). Gift stock is reserved together with product stock in one savepoint; `GiftStockShortage` subclasses `stock.InsufficientStock`, so the payment code treats an exhausted gift like an out-of-stock item. Inactive pool rows are hidden from new checkouts but already placed orders still get their gift. The seed creates the initial pool only while the pool is empty.
- **Gift hint** is shown only when gifts are on and at least one pool item is available.
- **Admin SMS** uses one space between short name and quantity, as in the example; it is triggered once (`Order.admin_sms_queued_at`) when an order enters paid_processing, one message per admin number. `resend_admin_sms` ignores the on/off toggle (it is an explicit request).
- **SMS digits:** SMS texts use Latin digits (better for OTP autofill and for every phone); the site itself keeps Persian digits.
- **Default SMS provider** in SiteSettings is Kavenegar; with an empty API key it runs as the console provider. The console provider can also be chosen explicitly.
- **Dashboard sales** = confirmed orders (paid_processing, shipped, delivered) counted by `paid_at`, `total` including shipping; canceled orders drop out. "This week" starts on Saturday, "this month" is the Jalali month, all in Tehran time. The chart is 30 daily bars as server-rendered inline SVG (no JS, no CDN), today on the left (RTL), with a native tooltip per day and a table view. One series, so one hue (light `#2F6FA8`, dark `#4F86C0`; contrast-checked).
- **Orders admin** is read-only except for the action buttons; orders cannot be added or deleted in the admin (cancel restores stock). The registration-date filter uses the same Jalali periods. Search normalises Persian digits. Excel export uses the change list's current filters/search (all pages) or the selected rows; numbers and mobiles stay text so leading zeros survive.
- **Tracking codes** are accepted as 6–40 characters of `0-9 A-Z a-z -` (Persian digits and spaces are normalised); Iran Post codes are usually 20–24 digits.
- **Packing slip** is a standalone print page (A5 per order, address label on top, items with gifts and a check box). It contains no prices (it goes into the parcel).
- **Customers admin** is a proxy of `User` limited to non-staff accounts; its totals and history include earlier guest orders with the same mobile (same rule as the user panel). Guest buyers without an account appear only in Orders.
- **Admin login** is mobile + password; django-axes counts failures per IP (5 → 1 hour, reset on success), and a wrong TOTP code also counts. Sessions started with the storefront SMS login carry `accounts.backends.SMSCodeBackend` and are not accepted by the admin, so an SMS code alone never opens the admin. TOTP (django-otp) is optional per admin; once a user has a confirmed device, every admin session of that user must be OTP-verified. django-otp's own throttling (1 s, 2 s, 4 s… after wrong codes) stays on.
- **Third-party admins** (django-q2, django-axes, django-otp) have no Persian translations; they were replaced by small Persian list-only admins (failed background jobs, login lockouts, 2FA devices) and the technical ones (successful tasks, schedules, queue) are hidden. Their sidebar names come from `ADMIN_GROUPS`; model metadata is not patched (that would create migrations inside those packages).
- **Secrets in SiteSettings** (SMS API key, gateway merchant id) are stored in the database as before but never rendered back into the page: the field shows a mask (last 4 characters), empty keeps the value, a checkbox clears it. They are not encrypted at rest; the database file is only readable inside the container and its backups.
- **Security headers:** Django sets HSTS, nosniff, `Referrer-Policy: same-origin`, COOP, `X-Frame-Options: DENY`; `core.middleware.SecurityHeadersMiddleware` adds a Content-Security-Policy (everything `'self'`; `'unsafe-inline'` for scripts/styles because the Django admin and TinyMCE need it; `frame-ancestors 'none'`) and a Permissions-Policy. Caddy limits request bodies to 20 MB and serves `/media/` with a sandboxing CSP. `form-action` is not restricted, because the payment start view redirects a POST to the gateway.
- **Uploads:** logo, banners and category images now use the same validator as product images (Pillow must open them as JPEG/PNG/WebP, size ≤ `PRODUCT_IMAGE_MAX_MB`); SVG and GIF are refused.
- **Production start guard:** `config/settings/prod.py` refuses to start with an empty or short (< 50 chars) `SECRET_KEY`, or with `ADMIN_URL` left as `admin/` or `panel-change-me/`.
